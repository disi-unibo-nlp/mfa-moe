## Findings requiring a changed plan

1. **Saved boolean outcomes flow unchanged into learned intervention targets.** `routing_study/execution.py:67-74` reads stored `is_correct`; a nonboolean becomes False, but an incorrect stored boolean is not re-scored. `runtime.py:197-202` serializes that value into calibration packets, and `execution.py:211` labels it `saved_calibration_outcome`. `calibration.py:26,35` uses it for identity lift, `:57-66` for Steer outcome arms, and `:173` passes it into margin calibration. Thus old correctness-based identity, Steer and margin target choices cannot be used as evidence of correctness-related experts. Rebind valid routing measurements to a separately versioned corrected outcome table; then refit policies and freeze new manifests. Do not mutate historical sealed packets.

2. **The proposed Steer estimator is explicitly unpaired even when paired data exist.** `routing_study/calibration.py:58-66` calculates within-question differences but labels them descriptive only; the ranking uses `mean(correct problem arms) - mean(incorrect problem arms)`. `:70-84` selects by that unpaired difference, with no requirement for any mixed-outcome question. Ten always-correct easy questions and ten always-incorrect hard questions can therefore satisfy support and generate targets with zero within-question evidence. This is an implementation-confirmed design limitation, not an allegation of holdout leakage. Rank targets on corrected within-question contrasts with adequate mixed-outcome question support if the estimand is routing versus correctness independent of question difficulty.

3. **Problem balancing does not control difficulty or benchmark.** Identity (`moe_identity_guiding/calibration.py:38-40,80-104`; compact equivalent `routing_study/calibration.py:25-43`) gives each question equal total weight, but still compares expert-weighted correctness against a global pooled baseline. Margin (`moe_margin_guiding/calibration.py:74-76,105-115`) likewise chooses bins by pooled correctness. These estimators can favor dataset/topic/easy-question expert specialization. Rescoring alone does not resolve this; the target-estimation design must change or these remain explicitly exploratory static policies.

4. **Legacy preparation selects out unscored/capped failures before even defining evaluation.** `moe_identity_guiding/prepare.py:17-22,28-45` and `moe_margin_guiding/prepare.py:22-27,33-50` discard nonboolean outcomes and absent routing first, then split the surviving question population. If cap failures are stored None, they disappear from both calibration and evaluation. Exclusions are counted in `split.json`, so these functions are not literally silent; downstream populations can still be misleading unless the counts and target population are reported. The `prepare_global` variants improve evaluation eligibility by splitting the entire generation population first, but still remove unscored calibration rows at identity `:127-136` and margin `:132-140`. Their holdouts do not depend on correctness. New `routing_study/prepare.py:99-131,158-193` also retains all attempts and uses outcome-independent question splits; it is not the source of the measurement campaign's truncated-cohort exclusion.

5. **Historical baseline reuse has no content-bound scoring implementation identity.** `moe_identity_guiding/execution.py:17-18,57-64` accepts a baseline by a fixed `scoring_contract` string and versions; `:69-101` checks only boolean type, not outcome provenance. Both guiding runners write the same string (`moe_identity_guiding/run.py:70`; margin run reuses the same execution/compare infrastructure). A scoring fix with an unchanged string and package versions can reuse stale labels. Correction needs an explicit scorer/outcome-table hash/version in reuse matching and result comparison, or a new immutable re-scored derivative with that binding. Existing texts and token IDs are reusable without regenerating them. The newer routing-study hashes `correlation_pipeline/scoring.py` in `common.py:77-89`, but not all transitive scoring dependencies such as its utility extractor; use an explicit complete scoring provenance record.

6. **Legacy calibration records extraction checkpoint metadata without enforcing compatibility.** Identity `calibration.py:35-37` rejects multiple generation models but does not require the sole source to equal `model`; `:50-52,115-117` records extraction configuration without validating its compatibility with the policy checkpoint. Margin `calibration.py:71-73` has the same single-model-only check; `read_margins()` at `:20-29` validates dimensions but not checkpoint identity. Consequently a same-shaped tensor from a different checkpoint can pass and produce expert targets. The identity README `:79-86` explicitly documents Unsloth replay to GPTQ transfer as an assumption. This is not accepted native GPTQ routing evidence. New routing-study calibration is stronger (`calibration.py:120-139`: exact checkpoint/backend/code, study hash, split membership and dispatch), and its guards should be retained.
