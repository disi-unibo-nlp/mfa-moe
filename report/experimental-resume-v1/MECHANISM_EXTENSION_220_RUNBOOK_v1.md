# Prospective 220-family mechanism extension v1

This is an **exploratory extension**, motivated by observed start-audit attrition in the separately registered 128-family mechanism pool. It was frozen before any extension reader rating or intervention outcome. It does not alter the registered pool, its 128-family feasibility gate, or its result label. The extension [family freeze](MECHANISM_EXTENSION_220_FAMILY_FREEZE_v1.json), seal `222f996be8f3a62b4ed71672ad776fa8649764bfc6d8f78da348abb0bc63b83c`, contains the full hash-ordered unused suffix of 220 families: 492 eligible after excluding 994 confirm-connected families, minus the 48 discovery, 128 mechanism, and 96 utility families already allocated. All 220 canonical representative questions and source-family identities are bound in the freeze.

The [CPU preparer](../../scripts/experimental_resume/prepare_mechanism_extension_220_v1.py) and [CPU wrapper](../../scripts/experimental_resume/run_mechanism_extension_cpu_v1.sh) define five sequential, sealed stages on `lrd_all_serial`: `units`, `detector`, `selection`, `frame`, `price`. The wrapper runs inside an already allocated Slurm job and calls each stage in its own `srun` step. The driver requires a real Slurm step on `lrd_all_serial`; hostname is deliberately ignored because valid serial nodes can have `login` names. The quickest safe layout is one CPU allocation with `all` so the native trace cache and queue wait are paid once. The checkpointed alternative uses `units` and then `rest` in a dependent CPU allocation. Neither layout runs GPU inference. Set `EXT_READER_MAX_WALL_SECONDS` to the **verified live GPU partition job limit** before `rest` or `all`; the price step rejects a missing or implausible limit. Do not infer a fixed 24-hour limit.

`units` reconstructs the existing first/centered/last contiguous 40-sentence native windows for every frozen representative, verifies trace digests and token ownership, and writes `dense-mechanism-extension-220/MECHANISM_EXTENSION_UNITS_v1.json` under the user-owned `tools/tmp/claude-analysis-2026-09-24/steering-v1/runs/routing-control-v1` tree. `detector` replays the unchanged frozen v2 detector over adjacent native prefixes and writes [audit](MECHANISM_EXTENSION_DETECTOR_AUDIT_v1.json). `selection` keeps at most three detector fires per family and each of the two supported transitions, `candidate_to_verify` and `approach_to_commit`, at no more than 8,192 native prefix tokens. It uses the same fixed event-hash order as the registered pool and writes [selection](MECHANISM_EXTENSION_START_SELECTION_v1.json). No outcome- or rating-dependent candidate replacement is allowed. `failed_check_to_revise` remains unsupported. The discovery-frozen target and exposure-matched random action dictionary is bound by seal. `frame` reconstructs the selected exact native prefixes and writes `dense-mechanism-extension-220/MECHANISM_EXTENSION_START_FRAME_v1.json` in the same user-owned staging tree. Every stage verifies its input seals and current producing-code hashes before proceeding. Stage outputs use a same-directory temporary file, `fsync`, and atomic rename under an exclusive file lock; a partial write cannot replace the last sealed artifact.

The original two independent Qwen start ratings remain the **primary eligibility criterion**. The observed possibility that both readers accept a target act already completed earlier in the native prefix motivates a prespecified [strict-veto sensitivity](../../scripts/experimental_resume/mechanism_extension_strict_veto_v1.py): two additional independent arm-blind ratings ask only whether the **same specific candidate or proposed approach in the trigger sentence** was substantively completed *before* that sentence. Unrelated earlier work cannot veto. This sensitivity includes a primary-accepted start only if both veto readers return a valid stopped `already_completed=false` result. Report the primary and strict-veto family/start denominators separately; never use the veto to replace a preselected start, alter primary eligibility after seeing intervention outcomes, or imply human ground truth. All reader messages contain only the original problem, emitted native prefix, current sentence, and transition criterion. They exclude future text, arm, answer correctness, and intervention fields.

The `price` stage writes [reader price](MECHANISM_EXTENSION_START_READER_PRICE_v1.json) using exact Qwen3.8 chat-template prompt lengths from the frozen frame, two primary plus two strict-veto ratings per selected start, a 1,024-token cap for **every** rating, the sealed prior bounded throughput, a 1.25 retry factor, complete 16-start batch shards, startup/shutdown, recovery loads, and the verified live wall limit. Its status stays `HOLD_EXTENSION_READER_DRIVER_AND_GPU_QUALIFICATION`: an extension-specific reader driver with v2-style attempt, assignment, batch, and resume receipts and a matching GPU profile qualification are still required. The extension intervention-generation manifest, complete-stage generation price, and receipt-bound runner are also future gates. Do not submit extension GPU readers or mechanism generation against this HOLD price.

Before detector counts are known, 220 families × 2 transitions × 3 starts allows at most **1,320 candidate starts**, hence at most **5,280 reader ratings** and **5,406,720 reader decode tokens** across primary and sensitivity ratings. Extrapolating the registered pool's 454 starts across 128 families gives roughly 780 extension candidates and about 55 two-GPU hours for four ratings per start; at the 1,320-start cap, the same mean prompt length and sealed throughput imply roughly 90–100 two-GPU hours, including rough sharding overhead. These are planning estimates, not a price or authorization to run. The exact sealed price follows the CPU frame. The finished 128-family detector audit took 66 seconds on 2 CPUs/16 GB; the complete 220-family CPU pipeline is not yet measured, so the one-hour allocation should be monitored and the sealed stage outputs allow retry. For later mechanism generation, the existing four one-action arms, two seeds, 1,024-token horizon, exact same-prefix execution, family-clustered intention-to-treat analysis, and complete-stage price/qualification rules remain requirements; no unsealed second action or action-order claim is introduced.

The extension CPU stages completed in Slurm job 59271965. They sealed 758 proposed starts across 220 families. The exact [source reader price](MECHANISM_EXTENSION_START_READER_PRICE_v1.json) is **51.443 two-GPU hours**, with 3,032 assigned ratings, 5,594,490 exact prompt tokens, and 3,104,768 capped decode tokens. Its first complete shard is rows 0–703 (704 starts); the second is rows 704–757 (54 starts). The source price remains HOLD pending a separate live qualification and rebind. This is an exploratory extension price; it is not part of the registered 128-family mechanism stage.

The extension-only [reader driver](../../scripts/experimental_resume/rate_mechanism_extension_start_readers_v1.py) and [source contract](../../scripts/experimental_resume/mechanism_extension_reader_contract_v1.py) now define four distinct channels per frozen start: primary readers 0 and 1, then strict-veto readers 0 and 1. Each channel has a deterministic seed, a 1,024-token cap, and an append-only attempted-batch ledger. The driver commits per-UID assignment receipts **before** each model call, then commits a channel batch and a four-channel combined batch atomically. An interrupted uncommitted attempt stays in the ledger and is counted; a resume uses the next attempt index and never treats an absent batch as a completed rating. Each priced shard has its own writer lock, manifest-bound `BINDING.json`, full assigned-UID `SUMMARY.json`, and output directory under `dense-mechanism-extension-220/ratings-v1-a7a9ea5d1e59cf76`. A later CPU `--seal-stage` verifies both shard summaries and all 758 assigned UIDs before writing `STAGE_COMPLETION.json`. Invalid JSON, capped generations, and failed votes remain in the assigned records and denominators.

The [qualification/rebind sealer](../../scripts/experimental_resume/seal_mechanism_extension_reader_v1.py) first writes [qualification manifest](MECHANISM_EXTENSION_READER_QUAL_MANIFEST_v1.json) with a complete one-hour upper-bound price for three frozen starts spanning both supported transitions and all four reader channels. Run the reader driver with `--qualify` in a separately priced two-GPU Slurm step using the same vLLM profile, Qwen snapshot, chat-template options, and 1,024-token cap as the full stage. It compares vLLM prompt token IDs against the exact Hugging Face chat template for both reader types and seals [qualification result](MECHANISM_EXTENSION_READER_QUAL_RESULT_v1.json) only on a live PASS. A failed or interrupted qualification remains a recorded attempt and needs a fresh remaining-cost review before retry. `rebind` then verifies the live result, source seals, code hashes, 24-hour shard bounds, and complete-stage 51.443 GPU-hour price, and writes [final reader price](MECHANISM_EXTENSION_START_READER_PRICE_v2.json) with `PASS_COMPLETE_STAGE`. Do not run `--shard-index 0` or `1` before that exact price exists. The qualification GPU ceiling is separate from the full-stage price.

The full-stage reader driver uses the same `vllm-cu129` Qwen3.8 environment and sampler profile as the qualified registered-pool reader, including `VLLM_USE_FLASHINFER_SAMPLER=0`, `VLLM_USE_V2_MODEL_RUNNER=0`, offline model cache, and per-job user-owned runtime directories. Each full shard should run as an independent two-GPU job within the price's verified 86,400-second wall limit; the first shard has little slack after its conservative work estimate, so monitoring and same-manifest recovery receipts matter. The driver itself does not submit jobs. No extension GPU job has been submitted by this work. [Seven CPU-pipeline tests](../../tests/experimental_resume/test_mechanism_extension_220_v1.py) and separate [reader receipt/qualification tests](../../tests/experimental_resume/test_mechanism_extension_reader_v1.py) cover the frozen source and recovery contract.
