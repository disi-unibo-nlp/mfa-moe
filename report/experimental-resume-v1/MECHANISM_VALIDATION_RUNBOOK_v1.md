# Mechanism generation v1: prepared, not launched

The frozen [selection](MECHANISM_START_SELECTION_v1.json) contains 454 proposed starts in the independent 128-family mechanism pool. Candidate-to-verify and approach-to-commit are the only supported starting conditions. Failed-check-to-revise is unsupported. The generation sealer consumes the complete v2 two-reader audit at `dense-mechanism/ratings-v2-7497e6aafbaf689c-497b2e8f57646826`; v1 ratings are rejected. Each reader result must cite a committed attempt in its sealed v2 ledger, and the combined batches, assignment receipts, summary and physical attempt counts must agree. Within each frozen family and transition, the first of the preselected events accepted by both readers is enrolled. No outcome-dependent replacement or new candidate search occurs.

The CPU [preparer](../../scripts/experimental_resume/prepare_mechanism_validation_v1.py) reconstructs every enrolled native prompt and prefix token ID from source traces, checking trace digests, the reader frame's exact token and text hashes, tokenizer identity and reasoning-prefix boundary. It also verifies that discovery, mechanism and utility parent family pools are disjoint. The manifest records accepted starts and distinct accepted families. If fewer than 128 distinct families pass, `registered_128_family_feasibility` is `FAIL` and the stage is explicitly an `exploratory_accepted_family_subset`; it cannot be reported as the registered 128-family validation.

Each accepted start receives two seeds and four arms: native, a second native draw, the discovery-frozen target expert set at bias +1, and one of the discovery-frozen exposure-matched random sets at bias +1. The random set is fixed per family across seeds. Every arm in a block receives the exact same prompt-plus-prefix token IDs and seed. Run positions are deterministically counterbalanced globally and within transition. The sole intervention pulse is at branch positions 0–255; the endpoint is 1,024 generated tokens. There is no frozen two-action template, so this stage has no reversed arm and cannot estimate a second transition or action order. All assigned caps, early closures, errors and nonfires remain in the receipts for family-clustered intention-to-treat analysis.

Before sealing the stage, both the v2 reader `SUMMARY.json` and the separate sealed [1,024-token engine qualification](MECHANISM_ENGINE_1024_QUAL_RESULT_v1.json) must exist and pass. The qualification must verify serial/eager execution, same-prefix four-arm requests, native isolation, recomputation after preemption and closure. The sealer requires a verified live partition wall limit through `--max-wall-seconds`; it prices the complete accepted-start stage from exact prompt tokens, all 1,024-token output caps, measured conservative serial throughput, retry factor, complete four-arm/two-seed row shards, required loads and shutdowns, and an additional recovery load. It writes [manifest](MECHANISM_VALIDATION_MANIFEST_v1.json) and [price](MECHANISM_VALIDATION_PRICE_v1.json) only after all inputs pass. No generic GPU-budget approval gate remains; the user has authorized the workload budget.

The [runner](../../scripts/experimental_resume/run_mechanism_validation_v1.py) requires the sealed `PASS_COMPLETE_STAGE` price and matching engine qualification. Each invocation names one priced `--shard-index` and writes under that shard's own manifest-bound output directory. The existing qualified worker writes attempted assignments, sealed batch receipts and routed-expert arrays; completed batches can be resumed only under the same manifest, source code and overlay. After all shards finish, `--seal-stage` checks every priced shard, route array and exact assigned UID before writing `STAGE_COMPLETION.json`. That receipt is an ungraded generation completion; dense blinded semantic labels and a family-clustered causal analysis are separate later work.

No mechanism preparation or generation job has been submitted by this work. The current gates are the running v2 reader audit, the independent full-horizon engine qualification, an observed live partition wall limit for the sharding price, and a successful CPU replay/seal. No claim about mechanism efficacy follows from the frozen starts or from this runbook.
