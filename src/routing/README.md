# src/routing

The analyses of native routing, with no intervention: does routing say which reasoning state a sentence is in, or which comes next, beyond what its text says? How do states follow one another? How should experts be kept when the budget is small? Everything here runs on the CPU from finished captures, labels and receipts. Launchers are in [`scripts/routing`](../../scripts/routing/README.md); run a module with `python -m routing.NAME` and `PYTHONPATH=src`.

Terms used below: a state is one of the seven sentence labels. RIG, the routing information gain, is the held-out loss of a model that sees text only minus the loss of the same model with routing added, in nats per sentence (positive favors routing). Questions, not attempts, are the unit: folds hold whole question families and intervals resample families.

Inputs and rules:

- `state_dynamics` reads a campaign folder with `CAMPAIGN.json` (`report/research-campaign-v3-20261014-r5-r2`) and recomputes everything into the new `--out` folder; the campaign is only read. The models are the ones named, else those `CAMPAIGN.json` lists. `expert_selection export` likewise takes the campaign folder (`report/expert-memory-study-v1`) and exports the models its `CAMPAIGN.json` lists.
- `present_state_readout`, `next_state_anticipation` and `next_state` read saved caches outside the repository (`ANALYSIS` in `src/store.py`) and compare their inputs with the frozen specification of the first run (`FROZEN.readout.v3.json`). `present_state_readout` and `next_state_anticipation` write to a new folder and take the cache folder as `--analysis-dir` (default `ANALYSIS`). The frozen specification names its inputs by absolute path, so the published run is reproduced only from the folder it used; with another `--analysis-dir` the comparison stops the run before any fit. `present_state_readout` reports a model whose cache is incomplete as INCOMPLETE and produces nothing for it; `next_state_anticipation` leaves missing cells incomplete. Neither recomputes a tensor, and the fixed grid and windows are never searched or widened.
- `efficiency_link.py` runs the frozen estimator of `efficiency_link_prereg.py` unchanged on eight models. That file keeps its original import line because its bytes are bound by the pre-registration hash, so `efficiency_link.py` loads it by path. Do not edit it. The seven original cells must equal the pre-registered ones. LFM2.5's signs were estimated after its interventions ran, and the receipt says so.
- `labelled_sentence_table` and `next_sentence_labels` read the same campaign folder as `state_dynamics` (it sits next to the study folder), the saved label files under `ANALYSIS`, and the traces. `next_sentence_labels` reproduces the published panel from the original sample alone (to 1e-12) before it adds a label, and labels enter only as the destination of a pair whose source is an original label. Occupancy, dwell and re-entry never read them. Its `judge` step is the one GPU step in this folder; it runs `steering.pulsed_steering.annotate_rows`, the same engine as the LFM2.5 labels. A rerun of `rebuild`, `plan` or `summary` into the same folders must reproduce the existing tables and receipts, or it stops: tables byte for byte, receipts apart from `module_sha256`, which records the code that wrote them and is not part of what they say (`store.publish(..., provenance=...)`). A relaunch of the whole chain therefore finishes.
- `next_state`, `lfm25_analyses`, `efficiency_link`, `next_sentence_labels` and `labelled_sentence_table` take the study folder as `--study` (default `STUDY_DATA_ROOT`, else `report/final-routing-20261015-r1`) and write their receipts there.
- `next_state` uses the machinery of `readout_fit.py` and `readout_analysis.py` unchanged, with the next state as target, and the same 522 questions.

## The helper packages and the frozen first runs

`depth_paths/`, `dynamics_routing/` and `reasoning_kinematics/` are the import closure (23 modules) of the two drivers `present_state_readout.py` and `next_state_anticipation.py`. The first published runs of these drivers hashed the same code from `/leonardo_work/IscrC_MIOSR/lmolfett/tools/tmp/claude-analysis-2026-09-24/forum/tests/r3_context/code/`, and the drivers compare their inputs with the frozen specification of those runs before fitting. Their root paths come from `store.ANALYSIS`. The drivers write to a new `--out` folder, record the hashes of the `routing` modules that ran (provenance only: renaming a folder does not change what the comparison checks), and refuse to run outside a Slurm batch job (they need `SLURM_JOB_ID` and `SLURMD_NODENAME`: the serial partition's nodes are called login08 and login13, and an `salloc` shell on a login node has no `SLURMD_NODENAME`). Neither driver can be rerun in full cheaply (19 and 84 core-hours).

`benchmark_accuracy.py` builds the benchmark accuracy tables from the outcome sidecar. `benchmark_inventory.py` writes the per-model inventory of the generated corpora into the output folder it is given; `report/model-analysis-review-20261008/` holds the inventory of the first run.
